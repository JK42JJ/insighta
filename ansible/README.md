# ansible

Host configuration for the production EC2 instance.

Scope is deliberately small. The infrastructure design moves this host's
responsibilities to a cluster; most of what is here is discarded at that
point. It exists because the design is months away and the gap it closes is
present now: **the nginx site configs live only on the instance.** Losing the
instance loses the routing rules, and a hand edit is detected by nothing.

Everything below was measured on the box on 2026-08-13. Values are not
guesses, and the playbooks assert them rather than assuming them.

## Prerequisite: reaching the host

Port 22 on the instance is restricted to an allow-listed egress IP. Ansible
connects over plain ssh and cannot do that negotiation itself, so open the
path first:

```bash
bash scripts/ssh-connect.sh --update-sg
```

The inventory addresses the host by its `~/.ssh/config` alias
(`insighta-ec2`), never by IP — this repository is public.

## Playbooks

| playbook | what it does | writes to prod |
|---|---|---|
| `bootstrap.yml` | docker + compose + deploy user | no-op on the current box; installs only with `-e bootstrap_install=yes` |
| `nginx.yml` | renders both site configs from templates | yes |
| `certbot-webroot.yml` | moves renewal off the nginx authenticator | yes, requires `-e confirm_certbot_migration=yes` |
| `verify.yml` | checks the running stack against the declaration | no |

Run order matters: `nginx.yml` must be applied before `certbot-webroot.yml`,
because the portfolio site has no ACME challenge location until the template
adds one.

```bash
cd ansible
ansible-playbook playbooks/nginx.yml --check --diff   # show the change, apply nothing
ansible-playbook playbooks/nginx.yml
ansible-playbook playbooks/nginx.yml                  # second run must be changed=0
```

`changed=0` on the second run is the completion criterion. A playbook that
reports changes every time is not describing the host, it is editing it.

## What is not here, and why

**There is no `deploy.yml`.** `.github/workflows/deploy.yml` already deploys
to this host over ssh. Adding an Ansible deploy path would put the same
desired state in two places on two schedules, which is the failure the
design's first principle exists to prevent. Deployment has one owner until
the CI path is retired. `verify.yml` covers what was actually missing: a
check that what deployed is what was meant.

## The two sites are in different states

| | `insighta.conf` | `portfolio` |
|---|---|---|
| origin | hand-written | generated by certbot's nginx installer |
| `# managed by Certbot` directives | 0 | 8 |
| ACME challenge location | already present | added by this role |
| routing | 10 `location` blocks, proxies to `:3000` and `:8081` | static file server |

This asymmetry is why the certbot migration is a separate, gated playbook.
Ansible can own `insighta.conf` outright — certbot never wrote to it. The
portfolio config *is* certbot output, so as long as `installer = nginx`
stands, certbot and Ansible are two writers of one file.

## Rollback

| change | how to undo |
|---|---|
| site config | `template` writes a timestamped `.backup` on the box before overwriting; off-box copies are in the private mirror at `backups/box/nginx/` |
| bad config | `nginx -t` runs before any reload. On failure the role restores the backups and fails without reloading — the running server is untouched |
| certbot migration | `sudo cp /etc/letsencrypt/renewal/NAME.conf.pre-webroot /etc/letsencrypt/renewal/NAME.conf` |

Certificates are never modified by these playbooks, so a failed run cannot
expire one. At the time of writing insighta.one runs to 2026-09-30 and
portfolio.insighta.one to 2026-11-01 — that is the window available to notice
and undo a mistake.
