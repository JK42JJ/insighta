# 브리프를 만다라 밖에 두기

2026-09-03. 설계 + 구현 기록. 아래 §1·§3 은 착수 후 바뀌었고, 바뀐 쪽이 지금 코드다.

## 용어

**에디토리얼.** `편집부` 는 쓰지 않는다 (James 지시, 2026-09-03).

브리프를 만드는 주체를 가리킬 때, 코드 주석·설계 문서·지면 서명 어디서든
`에디토리얼` 로 쓴다. 온톨로지의 `editorial_concept` · `editorial_video` ·
`editorial_issue` 타입 이름과 한 몸이 되도록 맞춘 것이고, 사람 조직을
연상시키는 `편집부` 보다 역할을 가리키는 편이 정확하다.

## 결정된 것

주간 브리프는 **만다라가 아니다.** 사이드바에 자기 자리를 갖는다.

버린 대안 두 개를 먼저 적는다. 되돌아올 때 근거가 필요하기 때문이다.

**(a) 브리프를 만다라로 만든다** — 구독하면 `ai-tech` 만다라가 생기고 매 호가
그 만다라의 노트가 된다. 사이드바도 노트 화면도 진입 경로도 하나도 새로 만들
필요가 없다. 오늘 안에 된다.

버린 이유는 소유권이다. 만다라는 **사용자가 만든 목표**이고 브리프는 **에디토리얼이
만든 간행물**이다. (a)는 둘을 같은 서랍에 넣는다. 그러면 사용자가 자기 만다라
목록에서 지울 수 없는 항목을 보게 되거나, 지울 수 있게 하면 구독이 끊긴다.
둘 다 설명할 수 없는 상태다.

**(c) 추천 5편을 카드로 꽂는다** — 기존 카드 시스템을 그대로 쓴다. 하지만
브리프를 "읽는" 경험이 사라지고 "카드를 받는" 경험이 된다. 이번 호의 본문 —
설정 파일이 신뢰 확인보다 먼저 실행된 이야기 — 은 카드 다섯 장으로 전달되지
않는다.

## 지금 있는 것

확인한 사실만 적는다.

```
사이드바 = 슬라이드 패널 3개 (Sidebar.tsx)
  ├ 만다라 패널   기본. settingsMode || isLearningRoute 면 왼쪽으로 빠짐
  ├ 학습 패널     isLearningRoute 면 오른쪽에서 들어옴
  └ 설정 패널     settingsMode 면 들어옴
  컨테이너는 하나(`relative flex-1`), 패널은 전부 `absolute inset-0`

노트 문서   note_documents(user_id, mandala_id, content_json)
            → 만다라 단위. 사용자 소유. TipTap. 편집·자동저장.

브리프      newsletter_issues(slug, category_key, issue_no, locale, content_json)
            → 전역. 에디토리얼 소유. IssueDocument. 읽기 전용.
            newsletter_subscriptions(user_id, category_key)  ← 누가 읽는지
            /brief/:slug 는 렌더되지만 사이드바에서 갈 방법이 없다.
```

`SIDEBAR_ROUTES` 에 `/brief` 를 넣는 수정(#1562)은 만다라 패널을 그대로 띄운다.
브리프를 읽는 동안 만다라 목록이 보이는 상태이고, 그건 임시 조치다.

## 설계

### 1. 네 번째 패널 — **폐기.** 만다라 패널 안의 접이식 목록으로 대신했다

원안은 브리프 경로에서 만다라 패널을 밀어내고 들어오는 네 번째 슬라이딩 패널이었다.
버린 이유는 James 지시(2026-09-03)로 배치가 **만다라 리스트 바로 위**로 정해졌기
때문이다. 같은 화면에 둘 다 있어야 하는 배치에서 "브리프를 읽는 동안 만다라 목록이
보일 이유가 없다" 는 전제가 성립하지 않는다.

지금 코드(`SidebarBriefEntry.tsx`)는 만다라 패널 안의 접이식 섹션이다.

```
브리프                          ▾        ← 접히면 여기에 안 읽음 합계
  AI 엔지니어링              ● 1        ← 구독 중인 도메인
  개발                                   ← 발행 전이어도 행은 있다
  + 브리프 추가                          → /brief
```

**목록의 출처는 구독이지 호가 아니다.** 처음에는 호 목록에서 도메인을 뽑았는데,
그러면 방금 구독한 브리프가 첫 호 발행 전까지 사이드바에서 사라진다 — 사용자가
그것을 찾을 유일한 순간에. `/brief/categories` 의 `subscribed=true` 를 목록으로,
호는 안 읽음 수를 세는 데만 쓴다.

### 2. 만다라 패널에 진입점 하나

브리프 패널은 브리프 경로에서만 보인다. 그러면 홈에서 브리프로 갈 방법이 없다.

자리는 **만다라 리스트 바로 위** — 미니맵 블록과 `Mandala fold list` 사이다.
(James 지시, 2026-09-03.)

```
Insighta BETA
새 만다라
템플릿 찾기
[카드 검색]
∨ 더 보기
[미니맵 3×3]
────────────────────
주간 브리프    ● 1        ← 여기
────────────────────
만다라 리스트
  · 인기 드라마 영화
  · ML 포트폴리오
  ...
```

위쪽(`SidebarTopSection`)이 아닌 이유: 그 블록은 **만드는** 동작이고
(새 만다라·템플릿 찾기·검색), 브리프는 **읽는** 것이다. 만다라 리스트와 같은
층에 두되 그 위에 놓으면, 둘 다 "내가 가진 것" 이라는 같은 의미가 된다.

배지는 안 읽은 호가 있을 때만. 없으면 숫자를 지운다. 매주 한 번 갱신되는
간행물이라 상시 배지는 소음이 된다.

### 3. 화면 두 개 — 목차와 카드 그리드

`/brief` 는 구독 관리 화면이다. 사이드바의 `+ 브리프 추가` 가 여기로 온다.

`/brief/c/:categoryKey` 는 **한 브리프의 호를 카드로 늘어놓은 그리드**다.
사이드바에서 도메인을 누르면 여기로 온다.

이 화면이 원안에 없었다. James 지시(2026-09-03): "만다라>주제선택>카드 리스트 와
같이 동일한 카드형태로 브리프가 보여지고 늘어나면 최신 카드가 정렬되어" — 즉
`만다라 → 주제 → 카드` 와 `브리프 → 도메인 → 카드` 가 같은 길이어야 한다.
도메인을 누르면 최신 호로 바로 보내던 초안은 그래서 버렸다: 그 길에는 "쌓인다"
는 감각이 없다.

**카드는 만다라의 카드다.** `InsightCardItemV2` 를 그대로 쓴다 (James 지시:
"카드는 니가 임의로 만들지말고 만다라 에서 사용하는카드를 활용해"). 다른 점은
셋뿐이고 전부 호가 무엇인지에서 나온다 — 드래그 불가(놓을 셀이 없다),
최신순 고정, 안 읽음 점.

호에 없는 것은 그럴듯하게가 아니라 정직하게 채운다. 표지는 그 호의 첫 꼭지
썸네일이다 — 브리프에는 고유 이미지가 없고, 만들어 붙이면 안에 있는 것과 아무
상관 없는 그림을 표지로 세우는 셈이 된다. 셀 번호는 `-1`, 만다라 id 는 `null`.

그리드를 `CardList` 로 공유하지 않은 이유: 그 모듈은 D&D 기계장치를 달고 있고
변경 가드 아래에 있다. 공유하려면 그것을 끌어오거나 잘라내야 한다.

카드 종류가 섞이는 사고는 `linkType` 필수화 + 종류 가드로 막는다 →
`docs/design/card-kind-required-2026-09-03.md`.

### 4. 읽음 상태

`newsletter_reads(user_id, slug, read_at)`.

구독과 분리한다. 구독은 카테고리 단위이고 읽음은 호 단위다. 한 테이블에 섞으면
"구독했지만 이번 호는 안 읽음" 을 표현할 수 없다.

읽음 기록 시점은 **도착**이다. 스크롤 깊이나 체류 시간으로 판정하지 않는다.
그건 측정할 수 있지만 이 제품이 지금 답해야 할 질문이 아니다.

### 5. API

```
GET  /api/v1/brief/subscribed     구독한 카테고리의 발행된 호 목록 (읽음 여부 포함)
GET  /api/v1/brief/categories     구독 가능한 카테고리 10개와 구독 여부
POST /api/v1/brief/subscribe      {categoryKey} — 이미 있음
POST /api/v1/brief/unsubscribe    {categoryKey} — 앱 안에서 끊기
POST /api/v1/brief/:slug/read     읽음 기록
```

`newsletter_unsubscribes` 는 그대로 둔다. 그건 로그인 없이 메일에서 끊는 경로고,
이건 앱 안에서 끊는 경로다. 둘은 다른 문제를 푼다 — 전자는 수신 거부, 후자는
구독 해지. 한쪽만 있어도 다른 쪽이 동작해야 한다.

### 6. 만다라와의 연결 — 검토 보류 (James, 2026-09-03)

**브리프는 당분간 그 자체로 유지한다.** 온톨로지 통합 여부는 나중에 검토한다.

기술적으로는 길이 있다. `shared` 도메인과 `RELATED_TO(domain: shared)` 는
스키마에 이미 있었고 — 내가 만든 것이 아니다 — 그런 쓰임을 예상한 설계다.
이으면 이런 모양이 된다.

```
goal(service) ──RELATED_TO──► editorial_concept(shared) ◄──MENTIONS── editorial_video(shared)
```

그러면 "당신의 MCP AI 에이전트 목표와 이번 호 세 번째 이야기가 이어집니다" 를
말할 수 있고, 브리프 목록에서 내 목표와 겹치는 호를 위로 올릴 수 있다.

지금 하지 않는 이유는 두 가지다.

**하나.** 프로드의 `shared` 노드가 0개다. 파이프라인이 프로드에서 아직 돌지
않았고, 없는 것을 이을 수는 없다.

**둘.** 사용자 `goal` 15,266개를 `editorial_concept` 26개에 잇는 것은 매칭
문제이고, 그 매칭이 맞는지 검증할 방법이 먼저 있어야 한다. 없이 이으면 엉뚱한
목표에 엉뚱한 호가 붙고, 그 오류는 사용자에게만 보인다.

브리프가 두세 호 쌓여 매칭을 검증할 데이터가 생긴 뒤에 다시 본다. 그때까지
`assert_edge_domain()` 트리거는 그대로 둔다 — 격리는 기본값이고, 여는 것이
결정이다.

## 만들 것

| | 무엇 | 크기 |
|---|---|---|
| 1 | `newsletter_reads` 테이블 | 작음 |
| 2 | API 4개 (위 목록 중 신규) | 중간 |
| 3 | ~~네 번째 패널~~ → `SidebarBriefEntry` 접이식 도메인 목록 | 중간 |
| 4 | 만다라 리스트 위 배치 + 배지 | 작음 |
| 5 | `/brief` 구독 화면 | 중간 |
| 6 | `/brief/:slug` 에서 읽음 기록 | 작음 |
| 7 | `/brief/c/:categoryKey` 카드 그리드 (착수 후 추가) | 중간 |

`/brief/:slug` 읽기 화면과 `newsletter_subscriptions` 는 이미 있다.

## 하지 않을 것

- 브리프를 만다라로 만들지 않는다.
- 브리프를 사용자가 편집할 수 있게 하지 않는다. 편집이 필요하면 "내 노트로
  담기" 가 별도 기능이고, 그때 사본이 생긴다.
- 읽음을 스크롤로 판정하지 않는다.
- 온톨로지 도메인 격리를 뚫지 않는다.
