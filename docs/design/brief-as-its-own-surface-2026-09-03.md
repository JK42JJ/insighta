# 브리프를 만다라 밖에 두기

2026-09-03. 설계만. 구현 전.

## 결정된 것

주간 브리프는 **만다라가 아니다.** 사이드바에 자기 자리를 갖는다.

버린 대안 두 개를 먼저 적는다. 되돌아올 때 근거가 필요하기 때문이다.

**(a) 브리프를 만다라로 만든다** — 구독하면 `ai-tech` 만다라가 생기고 매 호가
그 만다라의 노트가 된다. 사이드바도 노트 화면도 진입 경로도 하나도 새로 만들
필요가 없다. 오늘 안에 된다.

버린 이유는 소유권이다. 만다라는 **사용자가 만든 목표**이고 브리프는 **편집부가
만든 간행물**이다. (a)는 둘을 같은 서랍에 넣는다. 그러면 사용자가 자기 만다라
목록에서 지울 수 없는 항목을 보게 되거나, 지울 수 있게 하면 구독이 끊긴다.
둘 다 설명할 수 없는 상태다.

**(c) 추천 5편을 카드로 꽂는다** — 기존 카드 시스템을 그대로 쓴다. 하지만
브리프를 "읽는" 경험이 사라지고 "카드를 받는" 경험이 된다. 이번 호의 본문 —
설정 파일이 신뢰 확인보다 먼저 실행된 이야기 — 은 카드 다섯 장으로 전달되지
않는다.

## 지금 있는 것

확인한 사실만 적는다.

```
사이드바 = 슬라이드 패널 3개 (Sidebar.tsx)
  ├ 만다라 패널   기본. settingsMode || isLearningRoute 면 왼쪽으로 빠짐
  ├ 학습 패널     isLearningRoute 면 오른쪽에서 들어옴
  └ 설정 패널     settingsMode 면 들어옴
  컨테이너는 하나(`relative flex-1`), 패널은 전부 `absolute inset-0`

노트 문서   note_documents(user_id, mandala_id, content_json)
            → 만다라 단위. 사용자 소유. TipTap. 편집·자동저장.

브리프      newsletter_issues(slug, category_key, issue_no, locale, content_json)
            → 전역. 편집부 소유. IssueDocument. 읽기 전용.
            newsletter_subscriptions(user_id, category_key)  ← 누가 읽는지
            /brief/:slug 는 렌더되지만 사이드바에서 갈 방법이 없다.
```

`SIDEBAR_ROUTES` 에 `/brief` 를 넣는 수정(#1562)은 만다라 패널을 그대로 띄운다.
브리프를 읽는 동안 만다라 목록이 보이는 상태이고, 그건 임시 조치다.

## 설계

### 1. 네 번째 패널

```
  ├ 만다라 패널   기본
  ├ 학습 패널     isLearningRoute
  ├ 브리프 패널   isBriefRoute        ← 신규
  └ 설정 패널     settingsMode
```

브리프 패널이 담는 것:

```
주간 브리프
  AI 엔지니어링                     ← 구독 중인 카테고리
    제1호 · 9월 2일   ● 안 읽음
    (다음 호부터 여기 쌓임)

  + 다른 브리프 구독               ← 카테고리 10개 중 미구독분
```

만다라 패널과 같은 자리를 쓰되 내용이 다르다. 브리프를 읽는 동안 만다라 목록이
보일 이유가 없고, 만다라를 보는 동안 브리프 목록이 보일 이유도 없다.

### 2. 만다라 패널에 진입점 하나

브리프 패널은 브리프 경로에서만 보인다. 그러면 홈에서 브리프로 갈 방법이 없다.

자리는 **만다라 리스트 바로 위** — 미니맵 블록과 `Mandala fold list` 사이다.
(James 지시, 2026-09-03.)

```
Insighta BETA
새 만다라
템플릿 찾기
[카드 검색]
∨ 더 보기
[미니맵 3×3]
────────────────────
주간 브리프    ● 1        ← 여기
────────────────────
만다라 리스트
  · 인기 드라마 영화
  · ML 포트폴리오
  ...
```

위쪽(`SidebarTopSection`)이 아닌 이유: 그 블록은 **만드는** 동작이고
(새 만다라·템플릿 찾기·검색), 브리프는 **읽는** 것이다. 만다라 리스트와 같은
층에 두되 그 위에 놓으면, 둘 다 "내가 가진 것" 이라는 같은 의미가 된다.

배지는 안 읽은 호가 있을 때만. 없으면 숫자를 지운다. 매주 한 번 갱신되는
간행물이라 상시 배지는 소음이 된다.

### 3. 목록 화면

`/brief` (슬러그 없음) 은 구독한 브리프의 목차다. 사이드바에서 `주간 브리프`
를 누르면 여기로 온다. 최근 호가 하나뿐일 때는 바로 그 호로 보낼 수도 있으나,
그건 호가 쌓인 뒤에 정할 일이다. 지금은 목차를 만든다.

### 4. 읽음 상태

`newsletter_reads(user_id, slug, read_at)`.

구독과 분리한다. 구독은 카테고리 단위이고 읽음은 호 단위다. 한 테이블에 섞으면
"구독했지만 이번 호는 안 읽음" 을 표현할 수 없다.

읽음 기록 시점은 **도착**이다. 스크롤 깊이나 체류 시간으로 판정하지 않는다.
그건 측정할 수 있지만 이 제품이 지금 답해야 할 질문이 아니다.

### 5. API

```
GET  /api/v1/brief/subscribed     구독한 카테고리의 발행된 호 목록 (읽음 여부 포함)
GET  /api/v1/brief/categories     구독 가능한 카테고리 10개와 구독 여부
POST /api/v1/brief/subscribe      {categoryKey} — 이미 있음
POST /api/v1/brief/unsubscribe    {categoryKey} — 앱 안에서 끊기
POST /api/v1/brief/:slug/read     읽음 기록
```

`newsletter_unsubscribes` 는 그대로 둔다. 그건 로그인 없이 메일에서 끊는 경로고,
이건 앱 안에서 끊는 경로다. 둘은 다른 문제를 푼다 — 전자는 수신 거부, 후자는
구독 해지. 한쪽만 있어도 다른 쪽이 동작해야 한다.

### 6. 만다라와의 연결 — 나중

브리프의 개념(`editorial_concept`)과 사용자의 만다라 목표(`goal`) 사이에 경로가
있으면 "당신 목표와 이렇게 이어집니다" 를 말할 수 있다. 온톨로지에 두 노드가
모두 있으니 기술적으로는 가능하다.

지금은 하지 않는다. 도메인이 다르고(`shared` 대 `service`), 트리거가 도메인을
넘는 엣지를 막는다. 넘으려면 그 트리거에 예외를 뚫어야 하는데, 예외를 뚫는 것은
격리를 포기하는 것이다. 읽는 경험이 먼저 서고 나서 다시 본다.

## 만들 것

| | 무엇 | 크기 |
|---|---|---|
| 1 | `newsletter_reads` 테이블 | 작음 |
| 2 | API 4개 (위 목록 중 신규) | 중간 |
| 3 | `SidebarBriefSection` — 네 번째 패널 | 중간 |
| 4 | 만다라 패널 상단 진입점 + 배지 | 작음 |
| 5 | `/brief` 목차 화면 | 중간 |
| 6 | `/brief/:slug` 에서 읽음 기록 | 작음 |

`/brief/:slug` 읽기 화면과 `newsletter_subscriptions` 는 이미 있다.

## 하지 않을 것

- 브리프를 만다라로 만들지 않는다.
- 브리프를 사용자가 편집할 수 있게 하지 않는다. 편집이 필요하면 "내 노트로
  담기" 가 별도 기능이고, 그때 사본이 생긴다.
- 읽음을 스크롤로 판정하지 않는다.
- 온톨로지 도메인 격리를 뚫지 않는다.
