# 브리프는 만다라의 하위 항목이 아니다

2026-09-03. 앞선 구현을 폐기하고 다시 설계한다. James 판정: "만다라와는 별개로
리스트 하위에 + 버튼으로 만드는건 땜빵."

## 무엇이 땜빵이었나

내가 만든 것: 만다라 패널 안에 접이식 `브리프` 섹션, 그 아래 `+ 브리프 추가`
링크, 누르면 구독 체크리스트 화면(`/brief`).

세 군데가 틀렸다. 각각 다른 실수다.

**하나. `+` 는 이 제품에서 "만든다" 는 뜻이다.** `새 만다라` 는 만다라를
만든다. 그런데 `+ 브리프 추가` 는 아무것도 만들지 않는다 — 사용자는 브리프를
만들 수 없다. 고정된 열 개 중에서 켜는 것뿐이다. 같은 글리프를 다른 행위에
썼다. 이게 James 가 가리킨 지점이다.

**둘. 열 개는 고정이고 알려져 있다. 그걸 "추가" 뒤에 숨겼다.** 정확히 열 개고,
바뀌지 않는다. 숨길 것이 없는 목록을 숨기고, 보러 가려면 사이드바를 떠나야
하게 만들었다. **열 개 목록 자체가 표면이어야 하고, 구독은 각 행의 상태여야
한다.**

**셋. `/brief` 는 설정 화면인데 홈인 척한다.** 받은 호 목록과 구독 관리 목록을
한 페이지에 쌓았다. 둘은 하는 일이 다르고, 사이드바가 약속한 것은 둘 다
아니다.

근본 원인 하나로 모인다: **브리프를 만다라 패널 안에 넣었다.** 넣을 곳이
아니어서, 넣기 위한 장치(`+` 버튼, 별도 구독 페이지)가 필요했다. 장치가
땜빵이다.

## 원칙

이 제품에는 콘텐츠 축이 둘이다.

| | 만다라 | 브리프 |
|---|---|---|
| 소유 | 사용자 | 에디토리얼 |
| 만드는 주체 | 사용자 | 파이프라인 |
| 편집 | 가능 | 불가 (읽기 전용) |
| 늘어나는 계기 | 사용자가 만들 때 | 발행될 때 |
| 개수 | 사용자마다 다름 | 정확히 10 |

**둘은 대등하다.** 하나가 다른 하나의 하위 항목이 아니다. 사이드바가 그렇게
보여야 한다.

## 형태

사이드바 최상단에 축 전환. 두 축은 나란히 있고, 항상 보인다.

```
Insighta BETA                          [▣]
┌─────────────┬─────────────┐
│   만다라    │   브리프 ①  │        ← 대등. 안 읽음은 여기에
└─────────────┴─────────────┘
────────────────────────────────
        (선택된 축의 내용)
```

**만다라 축** — 지금 그대로. 새 만다라 · 템플릿 찾기 · 검색 · 미니맵 ·
만다라 리스트. 한 줄도 바꾸지 않는다.

**브리프 축** — 열 개가 전부 보인다.

```
AI 엔지니어링                    ③
개발                             ①
커리어                        구독 중
영어                            구독      ← hover 시 나타남
투자                            구독
소비                            구독
생산성                          구독
건강                            구독
스타트업                       준비 중
뉴스·트렌드                    준비 중
```

행의 상태는 넷이고, 전부 그 행 안에서 끝난다.

| 상태 | 보이는 것 | 클릭 |
|---|---|---|
| 구독 중 · 안 읽음 n | 진하게 + 배지 n | 카드 그리드로 |
| 구독 중 · 다 읽음 | 보통 | 카드 그리드로 |
| 미구독 · 발행 중 | 흐리게, hover 시 `구독` | 카드 그리드로 (읽을 수 있다) |
| 미구독 · 미발행 | 흐리게 + `준비 중` | 없음 |

`+` 가 사라진다. 만들 것이 없기 때문이다. 별도 구독 페이지가 사라진다. 구독은
행에 붙은 토글이고, 그 행은 이미 눈앞에 있다.

**미발행 도메인을 숨기지 않는 이유**: 목록이 곧 로드맵이다. 숨기면 제품이 실제보다
작아 보이고, 사용자는 "왜 AI 만 있지" 라고 묻게 된다. `준비 중` 은 답이다.

## 왜 새 패널이 아니라 축 전환인가

원안(`brief-as-its-own-surface` §1)은 네 번째 슬라이딩 패널이었다. 패널 기계는
이미 있다 — `Sidebar.tsx` 는 `absolute inset-0` 패널 셋을 `settingsMode` ·
`isLearningRoute` 로 밀어낸다. 브리프 패널을 넣는 것은 그 구조를 **쓰는**
것이지 새로 만드는 게 아니다.

원안이 막힌 곳은 하나였다: **브리프 경로에서만 보이는 패널은 홈에서 갈 방법이
없다.** 그래서 진입점이 필요했고, 진입점을 만다라 패널에 박은 것이 땜빵의
시작이었다.

축 전환이 그 구멍을 메운다. 패널은 그대로 네 개, 전환은 라우트가 아니라 사용자
선택. `설정`·`학습` 패널은 지금처럼 라우트가 밀어낸다 — 그건 "지금 하는 일"
이고, 만다라/브리프는 "무엇을 보는가" 라서 층이 다르다.

## 화면

| 경로 | 지금 | 바뀐 뒤 |
|---|---|---|
| `/brief` | 받은 호 + 구독 관리 (설정 화면) | **삭제.** `/brief/c/<첫 구독>` 으로, 구독 0이면 브리프 축을 연 홈으로 |
| `/brief/c/:key` | 한 도메인의 호 카드 그리드 | 그대로. 이건 맞았다 |
| `/brief/:slug` | 호 읽기 | 그대로 |

`/brief` 를 지우는 이유: 그 페이지가 하던 두 일이 각각 갈 곳이 생겼다. 구독
관리는 사이드바 행으로, 받은 호는 도메인별 그리드로. 남는 것이 없다.

## 접힌 레일

지금은 `collapsed` 면 브리프도 만다라도 `null` 을 반환한다. 축 전환은 접힌
상태에서도 **아이콘 두 개**로 남는다 — 접힌 레일에서 축을 못 바꾸면, 축을
바꾸려고 사이드바를 펴야 하고 그건 전환이 아니라 우회다.

## 모바일

James: "브리프는 모바일을 위한 개념이 더 크다."

모바일은 사이드바가 없다. `/mobile` 다이얼이 표면이고, 브리프는 거기서
**휠의 한 자리**여야 한다 — 데스크톱 축 전환의 모바일 대응물. 이번 설계에는
넣지 않는다. 이유는 다이얼의 입력 표면 4종(dispatchNotch · corePress ·
menuBack/goHome · wheelzone)을 전수 판정해야 하고, 그건 이 문서가 답하는
질문이 아니다.

**다만 지금 막혀 있는 것은 이번에 푼다**: `/brief` 가
`ALLOWED_MOBILE_PATH_PREFIXES` 에 없어서, 메일 CTA 를 폰에서 누르면
`/landing` 으로 튕긴다. 발행하면 바로 터지는 경로다. 읽기 화면
(`/brief/:slug`)만 허용하고, 앱 셸이 필요한 축·그리드는 열지 않는다.

## 지우는 것

- `SidebarBriefEntry.tsx` — 접이식 섹션 + `+ 브리프 추가`
- `BriefIndexPage.tsx` — 구독 관리 화면
- `/brief` 라우트

새로 만드는 것: `SidebarAxisSwitch` (전환), `SidebarBriefSection` (열 개 행).
`BriefCategoryPage` · `briefIssueToInsightCard` · `card-kind` 는 그대로 쓴다 —
카드 쪽 작업은 이 문서가 뒤집지 않는다.

## 먼저 고칠 것 — 설계와 무관한 결함

**브리프 API 다섯 개가 전부 401 을 돌려준다.** 로그인 상태에서도 그렇다.

```
/api/v1/mandalas/list      200  x24
/api/v1/brief/subscribed   401  x13
/api/v1/brief/categories   401  x13
```

`authenticate` 는 `request.user.userId` 를 세팅하는데 브리프 핸들러 5곳이 전부
`request.user.id` 를 읽는다. `(request.user as { id?: string })` 캐스트가 실제
타입을 지워서 타입 검사도 통과했다.

이게 화면이 비어 보인 진짜 이유다. 설계를 어떻게 바꾸든 이건 먼저 고쳐야 한다.
같은 실수를 막으려면 `getUserId(request)` 를 공용 헬퍼 하나로 두어야 한다 —
지금 `search.ts` · `settings.ts` · `mandalas.ts` 에 각각 다른 사본이 있고, 그
분산이 여섯 번째 사본을 잘못 쓰게 만든 조건이다.
