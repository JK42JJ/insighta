# 대안 절차: 이메일 · 매직 링크 중심 초대로 전환

- 용도: 금요일 시험 5b-4(**신규 가입 비활성화 후, 미리 만든 초대 계정의 Google 로그인**)가 실패했을 때 쓴다. 시험 전에 읽을 수 있게 미리 준비한 문서다.
- 실행 주체: James. 대시보드 작업과 메일 발송(R02)은 CC 가 하지 않는다.
- 표기: "추측"은 읽지 않고 추론한 것, "미검증"은 확인하지 못한 것. 이 문서의 모든 동작은 **아직 시험하지 않았다**.

## 1. 언제 쓰는가

| 시험 결과 | 의미 | 조치 |
|---|---|---|
| 5b-3 실패 (처음 보는 Google 계정 B 가 가입됨) | 설정만으로는 초대 전용이 성립하지 않는다 | **이 문서가 아니다.** 코드 게이트(INV-1)를 앞당길지, 출시 방식을 바꿀지 James 가 판단 |
| 5b-3 통과, **5b-4 실패** | 차단은 되지만 초대 사용자도 Google 로 로그인하지 못한다 (또는 이메일이 같은데 별도 계정으로 취급) | **이 문서를 쓴다** |
| 5b-3 · 5b-4 통과, 5b-5 실패 | Google 은 되지만 매직 링크가 안 된다 | Google 중심으로 안내하고 매직 링크는 안내하지 않는다 (이 문서의 반대 방향) |
| 5b-3 · 5b-4 · 5b-5 모두 실패 | 신규 가입 비활성화가 기존 사용자 로그인에 영향 | 신규 가입을 다시 활성화하고 중단. 출시 방식 재검토 |

## 2. 전환 후의 로그인 경로

| 경로 | 초대 사용자 | 비고 |
|---|---|---|
| 이메일 입력 → 매직 링크 | **사용** | 로그인 화면이 매직 링크를 지원한다 (`AuthContext.tsx`: Google, 이메일 + 비밀번호, 매직 링크). 신규 가입이 꺼져 있으면 미초대 이메일은 링크로도 계정이 생기지 않아야 한다 (5b-5 에서 확인, 미검증) |
| Google | 안내하지 않음 | 5b-4 실패 상태. 시도하면 거부되거나 별도 계정이 생길 수 있다 |
| 이메일 + 비밀번호 | 기본 안내 대상 아님 | 임시 비밀번호를 만들어 전달하는 방식은 자격 증명 배포가 되므로 권하지 않는다 |

## 3. 절차 (James)

| # | 단계 | 확인 |
|---|---|---|
| 1 | 초대 대상 이메일 목록을 확정한다 (S7a, 목요일까지 James 가 정함) | 목록 · 인원 |
| 2 | 각 대상 계정이 Supabase 에 **이미 존재**하는지 확인한다. 없으면 대시보드에서 사전 생성한다 (5b-1 과 같은 방식). 이메일 확인 상태 옵션이 있으면 확인된 상태로 만든다 (옵션 존재 여부 미검증) | 사용자 목록에 대상 전원 |
| 3 | 앱 쪽 초대 상태: 관리자 화면(`AdminBetaCampaign`)에서 대상을 `invited` 로 처리한다. 이 동작은 초대 이메일을 보낸다 (`mark-invited` → `sendBetaInviteEmail`) → **발송은 James 가 직접** (R02) | `beta_applications.status='invited'` |
| 4 | `beta_signup_mode=invite_only` 와 Supabase 신규 가입 비활성화 상태를 확인한다 | 기록 |
| 5 | 사용자 안내문(OPS-2)을 이 경로 기준으로 쓴다 (아래 4절). 발송은 James 의 "보내" 후 | — |
| 6 | 대상 1명(본인 부계정 등)으로 매직 링크 로그인 → 첫 사용(OPS-1 스모크) | 통과 |
| 7 | pro 30일 부여(INV-4), 만료일 기록 확인 | `tier_expires_at` |

## 4. 안내문에 들어갈 내용 (초안 조각, 발송 아님)

- 로그인 방법: "로그인 화면에서 **Google 버튼을 누르지 말고** 초대받은 이메일 주소를 입력해 메일로 오는 링크로 들어오세요."
- 메일이 오지 않을 때: 스팸함 확인, 몇 분 뒤 재시도, 피드백 경로로 알림 (경로는 OPS-2 에서 확정).
- Google 로 이미 시도해 오류를 본 사용자: 같은 이메일로 매직 링크를 쓰면 된다 (중복 계정이 생겼는지는 6절의 확인으로 본다).

문구의 최종 확정과 발송은 James.

## 5. 위험

| 위험 | 대응 |
|---|---|
| 매직 링크 메일의 발송 한도 · 지연. 인증 메일이 Supabase 기본 발송 경로이면 시간당 한도가 낮을 수 있다 (기억 기반, **미검증**) | 초대 인원이 많으면 월요일에 시차를 두고 안내하거나 자체 SMTP 설정을 검토. 목요일에 대시보드의 메일 설정을 확인 |
| 메일이 스팸으로 분류됨 | 안내문에 발신 주소를 적는다. 대상 1명으로 선확인 |
| 같은 이메일로 Google 과 매직 링크를 오가며 중복 계정이 생김 | 신규 가입이 꺼져 있으면 새 계정이 만들어지지 않아야 한다. 월요일 점검에서 `auth.users` 의 이메일 중복을 읽기 전용으로 확인 |
| 초대 사용자가 Google 만 쓰던 습관으로 접근 실패 | 안내문 첫 줄에 로그인 방법을 둔다. 오류 문구와 대응을 지원 응답에 미리 준비 |

## 6. 확인 항목 (월요일 아침)

- 초대 사용자 전원의 첫 로그인 성공 수 (읽기 전용 조회)
- `auth.users` 이메일 중복 없음
- 매직 링크 미도착 문의 건수
- 문제가 있으면 이 절차를 그대로 유지할지, Google 경로 복구를 시도할지 James 가 판단

## 7. 되돌리기

이 절차는 로그인 안내만 바꾼다. 시험으로 바꾼 설정(신규 가입 비활성화)은 대시보드에서 복원할 수 있다. 사용자 계정 사전 생성은 되돌릴 수 있으나 계정이 쓰인 뒤에는 삭제하지 않는다 (R14).
