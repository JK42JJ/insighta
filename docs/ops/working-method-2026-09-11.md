### 1.2 패턴 네 가지

1. **턴 단위 작업.** 목표 대신 지시가 들어오고, 세션은 인덱스와 규칙을 읽고 맥락 없이 시작한다. 그래서 같은 설계를 다시 한다. 마스터 스펙을 보관하지 않아 뉴스레터 설계를 두 번 했고, 위저드 수정 4 PR 은 전량 원복됐고, 사업계획서는 다섯 번 썼다.
2. **규칙이 사건 기록으로 자란다.** CLAUDE.md 의 규칙 대부분이 "CP391→CP396→CP412" 식 사건 서술이다. AWS 영상이 경고한 "금지 사항 블로팅" 그 자체다. 프롬프트 규칙은 집행력이 없다. 집행되는 것은 훅과 CI 뿐인데 그 수는 규칙 수의 십분의 일이다.
3. **완료의 정의가 PR 머지다.** 배포 검증은 있지만 "이 기능이 사용자에게 어떤 결과를 내야 하는가" 라는 수용 기준이 작업 단위에 없다. 그래서 140개가 머지돼도 제품은 완성에 가까워지지 않는다.
4. **병렬 세션이 계획 없이 병렬이다.** insighta · career · 감독관 세션이 각자 방향(보안 · 사업계획 · 뉴스레터 · 이력서)을 잡고, 판단이 채팅 붙여넣기로 오간다. 한 시간에 방향이 두 번 바뀐 날이 오늘이다.

### 1.3 같은 날의 대조 실험

같은 세션, 같은 모델에서 오늘 두 방식이 나란히 있었다.

| | 오전 (진단 · 설계 · 결정 대기) | 오후 (목표 한 줄 · 자율 실행) |
|---|---|---|
| 입력 | "보안 설계를 추가해" → 7 Phase 설계 → 결정 6건 대기 → "뭘 하기는 하는거야" | "정적 키 0, 기록·탐지·복원, 비용 0. 실행해" |
| 소요 | 약 3시간 | 약 2시간 |
| 산출 | 문서 3편, 결정 요청 | PR 6개 머지, prod 적용 32 리소스, OIDC 전환 검증 3회, 복원 리허설 성공, 증거표 |
| James 턴 | 8회 이상 | 2회(규칙 추가 1, 확인 1) |

차이는 모델이 아니라 **목표 · 제약 · 검증 기준이 명시됐는가** 였다. 이것이 개편의 전부다.

## 2. 원칙 — 세 영상에서 가져오는 것

| # | 원칙 | 출처 | 우리 말로 |

## 3. 새 작업 방식

### 3.1 작업 단위 = 워크 오더 (네 요소)

```
# WO-2026-09-11-security-stage1
목표      정적 자격증명 0 · 계정 기록·탐지·알림 · 복원 검증. 비용 0.
맥락      docs/security/cloud-security-architecture-2026-09-11.md §5 Stage 1
제약      유료 서비스 금지 · .env 불변 · 머지=apply 인식 · 이력서 파일 접근 금지
검증 기준 credential report 활성 키 = admin 1개 · OIDC 워크플로 성공 1회 · IsLogging=true · 알람 ≥3 · 복원 리허설 0 mismatch
되돌릴 수 없는 것(James) MFA 등록 · OAuth secret 재발급 · SNS 구독 확인
```

- 위치 `docs/work-orders/`. 한 파일 = 한 단위. 상태는 파일 머리에(`open / running / verified / closed`).
- 에이전트는 시작 전에 검증 기준을 자기 말로 다시 적고, 기준이 비면 제안한다. James 는 오더를 승인하지 단계를 승인하지 않는다.
- 오더 없이는 코드를 바꾸지 않는다. "이왕이면 이것도" 는 새 오더다.

### 3.2 제품 스펙 = 단일 기록

- `docs/spec/README.md` 하나에서 시작. 표면마다 한 절: 목적 · 고객 · 수용 기준 · 검증 명령 · 상태(`live / maintenance / deprecated`).
- 핸드오프 33개는 스펙으로 흡수한 뒤 `docs/handoffs/archive/` 로. 새 핸드오프는 만들지 않는다. 세션 인계는 스펙 + 열린 워크 오더로 한다.
- 새 세션이 읽는 것은 스펙 · 열린 오더 · 훅으로 집행되는 규칙표 세 가지다. 부팅 로드 목표 40만 자 → 5만 자.

### 3.3 완료의 정의 네 칸

| 칸 | 내용 | 집행 |
|---|---|---|
| 테스트 | 새 함수 · 훅 · API 마다 1개, 버그 수정마다 회귀 1개 | CI |
| 자동 검증 | CI + `/verify` + prod 확인 명령(오더의 검증 기준) 통과 | `/ship` 게이트 |
| 스펙 갱신 | 바뀐 표면의 스펙 절이 같은 PR 에 있다 | `/ship` 게이트 |
| 검증 리포트 | 변경 · 검증 방법 · 미검증 항목 · 판단 요청 | PR 본문 템플릿 |

"완료" 라는 단어는 네 칸이 찬 뒤에만 쓴다. 하나라도 비면 "진행 중, 남은 것 X".

### 3.4 결정 분류

| 되돌릴 수 있음 → 에이전트가 실행하고 기록 | 되돌릴 수 없음 → James |
|---|---|
| 코드 · 차트 · 문서 변경, 브랜치 · PR, 스테이징 배포, 읽기 조회, 로컬 실험, 워크트리 정리, 규칙 삭제 제안 | 메일 · 알림 발송, 결제 · 계정 변경, 데이터 삭제, 비용 발생, 제품 방향, 외부 공개, 시크릿 재발급 |

지금의 "계획 → 승인 → 실행" 은 왼쪽 열에도 적용돼 베이비시팅 루프를 만든다. 왼쪽 열은 실행 후 다이제스트로 보고한다.

### 3.5 하루의 리듬

- **아침 10분** — James 가 워크 오더 1~3개를 승인한다. 오더는 전날 에이전트가 초안을 써 둔다.
- **낮** — 에이전트가 워크트리 · 백그라운드 에이전트로 자율 실행한다. 막히면 질문 큐(`docs/work-orders/QUESTIONS.md`)에 적고 다음 일을 한다. 채팅으로 되묻지 않는다.
- **저녁** — 다이제스트 하나. 변경 · 검증 · 미검증 · 질문 · 되돌릴 수 없는 결정 요청. James 는 결정을 3줄로 남긴다. 그 3줄이 다음 오더가 된다.
- **주 1회** — 프루닝 리뷰. 규칙 삭제 수 ≥ 추가 수. 스파게티 지표(§5) 확인.

### 3.6 James 의 검토 루틴 (유창성의 착각 방지)

다이제스트를 읽은 뒤 3줄을 쓴다. ① 핵심 변화 세 가지 ② 근거(어떤 검증이 그것을 증명하나) ③ 반례 또는 의문 하나. 이 3줄을 에이전트가 스펙과 오더에 반영한다. 코드를 읽는 대신 도식과 검증 리포트를 읽는다.

### 3.7 세션 간 조정

- 세션 역할 고정: insighta 서비스 · career · 감독관(ontology). 역할 밖 파일은 건드리지 않는다.
- 공유 보드 하나: 열린 워크 오더 목록. 세션은 보드에서 오더를 가져간다.
- 방향 결정은 감독관 채팅 한 곳에서만. 다른 세션은 방향을 제안하되 결정하지 않는다.
