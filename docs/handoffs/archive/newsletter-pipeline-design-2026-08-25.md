## 0. 이 설계가 존재하는 이유 — 창간호 1차 시도의 실패

만들어 봤고, 실패했다. 실패 원인이 설계 근거라 먼저 적는다.

수확은 **2,714편**(롱폼 1,042편) 성공했다. 그런데 집필자에게 넘어간 것은 **69편(6.6%)** 이었고,
그마저 사람이 조회수로 자른 뒤 **덩어리 4개로 미리 묶고 해설까지 붙여서** 넘겼다.

결과는 예정돼 있었다. 넘긴 문장과 나온 기사를 나란히 놓으면:

| 넘긴 것 | 나온 기사 |
|---|---|
| 제목이 하나같이 클로드 코드를 기준점으로 삼는다 | 전부 클로드 코드를 걸고 이야기한다 |
| 영어권에 같은 소재가 한 편도 없다 | 영어권에는 같은 소재가 한 편도 없었다 |

**번역만 일어났다.** 집필자는 편집을 하지 않았다. 이미 끝난 편집에 문체만 입혔다.
게다가 지시문에 *"이 비대칭이 이번 호의 축이 될 수 있다"* 고 축까지 지정해서 보냈다.

여기서 나오는 설계 원칙이 이 문서 전체를 규정한다.

> **원칙 1 — 사람은 후보를 자르지 않는다.**
> 자르는 것은 기록되는 기계 게이트만 한다. 사람은 살아남은 것 중에서 고른다.
>
> **원칙 2 — 집필자에게는 결론이 아니라 증거를 준다.**
> 덩어리·순위·해설을 미리 만들어 주면 그것이 그대로 기사가 된다.
>
> **원칙 3 — 비싼 판정은 소수에만.**
> 1,042편을 전부 깊이 읽을 필요는 없다. 떨어진 이유를 세면 된다.

두 번째 결함도 있었다. `snippet.description` 을 수확해 놓고 한 줄도 넘기지 않았다.
그래서 기사가 스스로 자백했다 — *"제목과 채널, 길이만 보고 고른 것이다."*
그것은 겸손이 아니라 **재료 부족의 자백**이다.

## 1. 이미 있는 것 — 새로 만들지 않는다

전수 확인했다. 파이프라인 8단계 중 **새로 만들어야 하는 것은 2개뿐**이다.

| 단계 | 필요한 것 | 이미 있는 것 | 경로 |
|---|---|---|---|
| 수확 | 검색 + 통계, 키 로테이션 | `searchVideos` · `videosBatch` · 검색키 8개 자동 failover | `skills/plugins/video-discover/v2/youtube-client.ts` |
| 탈락 기록 | 후보별 탈락 사유 | `writeSearchTrace()` — 후보 23,394행 적재 실적 | `modules/search-trace/index.ts` |
| 유해·무관 판정 | 2축 판정 | `topic-judge` — safe / learnable, 판정 영속화 | `modules/curation/topic-judge.ts` |
| 도메인 분류 | 9축 | `DOMAIN_SLUGS` + KO/EN 라벨 | `config/domains.ts` |
| 자막 | 자막 취득 | `caption/extractor` — Innertube + Mac Mini/Azure 프록시 | `modules/caption/extractor.ts` |
| 인용 근거 | 타임스탬프 달린 구간 | v2 rich summary — `entities` + `sections{timestamp, relevance_pct}` | `modules/skills/summary-gate.ts` |
| 비용 귀속 | 호출별 원가 | `llm_call_logs` + `call-logger` | `modules/llm/call-logger.ts` |
| 스케줄 | 주간 실행 | pg-boss + `curation-weekly` cron | `modules/queue/handlers/` |
| 발송 | 대상·템플릿·발송 | `email/broadcast` · `templates` · `transactional` | `modules/email/` |
| **채널 원장** | **주간 Top 100 진입·이탈** | **없음 — 신규** | §5 |
| **발행물 저장** | **호수·초안·확정본·정정** | **없음 — 신규** | §7 |

법적 제약 하나가 설계를 규정한다. `caption/extractor` 주석:

> *"LEGAL: Transcripts are NOT persisted on the server. Only LLM-generated summaries are stored."*

**자막 원문을 저장하지 않는다.** 팩트체크는 자막이 아니라 **v2 요약의 타임스탬프 구간**을 근거로 삼는다.
이것이 §4 인용 방식을 결정한다.

## 2. 파이프라인 — 8단계

각 단계는 **무엇을 떨어뜨렸는지 기록**한다. 기록이 없으면 그 단계는 없는 것과 같다.
아래 숫자는 이번 주 AI·기술 도메인 실측이다.

```
S0  수확          2,714편        넓게. 여기서 좁히면 나중에 못 넓힌다
S1  형식 게이트    → 1,042편      쇼츠·4분 미만·중복. 기계적, LLM 0
S2  도메인 게이트  → [미측정]      카테고리 27·28 이미 적용됨(유입 단계)
S3  판정          → [미측정]      topic-judge 2축. 여기부터 비용 발생
S4  심층          → 상위 30편     자막 → v2 요약. 가장 비쌈
S5  교차검증      → 인용 가능분    같은 주장 몇 채널에서 독립 발생했나
S6  통계          깔때기 전체      떨어진 이유의 분포가 곧 기사
S7  집필·검수     사람            증거만 받고, 축은 스스로 세운다
```

### S0 — 수확

이번 주 실적: 쿼리 80개(한 20 × 영 20 × 카테고리 2), 호출 80회, **실패 0**, 8,000 units.

**신선도 3종이 핵심이다.** 스케줄 수집기가 지금 안 하고 있는 것들이다.

```
order: 'date'          수집기는 'relevance' 로 두는데, 클라이언트가 그 값이면
                       파라미터를 아예 안 보낸다. 결과가 인기순으로 기울어 낡는다
publishedAfter: 7d     기간 한정
videoCategoryId        27 교육 · 28 과학기술
```

**카테고리 한정이 유입 오염을 막는다.** 이전 시도에서 제목에 `AI` 가 든 주식 채널
(소수몽키·수페TV·채국장)이 대량 유입돼 기사의 축까지 오염시켰다.
카테고리를 걸자 상위 채널이 전부 기술 채널로 바뀌었다. 사후 필터가 아니라 유입 차단이다.

> **API 함정 (2026-08-25 실측)**: `videoCategoryId` 에 CSV(`'27,28'`)를 넘기면 **HTTP 400**.
> 단일 값만 받는다. 카테고리마다 따로 호출해야 한다.
> 클라이언트 JSDoc 은 *"CSV of videoCategoryId values (e.g. '27,28,26')"* 라고 적고 있는데 **틀렸다.**
> 지금 CSV 를 넘기는 호출부가 없어 사고는 없지만, 주석을 믿으면 400 을 맞는다. 주석 수정 필요.

**쿼리 설계.** 한국어판이라도 영어 소스를 함께 가져온다. 이번 주 실측이 이유를 보여준다 —
딥시크 하네스는 영어 11편 대 한국어 4편, 퓨리오사AI 는 한국어 5편 대 영어 0편.
**한쪽만 보면 둘 다 못 본다.**

### S1 — 형식 게이트 (LLM 0, 비용 0)

| 규칙 | 이번 주 탈락 |
|---|---|
| 쇼츠 / 4분 미만 | 1,672편 |
| 동일 video_id 중복 | 수확 중 제거 |
| 동일 채널 같은 주 N편 초과 | [미측정] — §5 채널 원장과 연동 |

### S2 — 도메인 게이트

유입 시점 카테고리 한정으로 이미 걸러진다. 9축 택소노미 태깅은 이 단계에서 붙인다.

### S3 — 판정 (비용 시작)

`topic-judge` 재사용. 2축: `safe`(학습 제품에 노출 가능한가) · `learnable`(주간 학습거리가 되는가).

이 모듈이 존재하는 이유가 그대로 뉴스레터에 적용된다 — 모듈 주석:

> *"trend_signals 상위 20 중 대략 3분의 1만 학습 주제였고, 나머지는 사람·장소·노래 제목·교회 이름·웹소설이었다.
> 유해어는 0.08% 인데 상위에 있었다. rising 이 곧 인기이기 때문이다."*

**판정 결과를 영속화**하므로 재실행 비용이 0이다. 이미 그렇게 설계돼 있다.

여기서 **낚시·과장 축을 하나 더 붙인다**. 이번 주 제외 사례:
`"7세 아이 키우며 순수익 월 2,000만 원"`, `"이런 영상으로 월 300 벌었습니다"`.
확인 불가능한 금액을 제목에 건 것. 지금은 사람이 뺐고, **판정으로 옮겨야 자동화된다.**

### S4 — 심층 (가장 비쌈, 상위 30편에만)

`caption/extractor` → v2 rich summary. 산출물이 곧 인용 근거다:

```
entities            개체 2개 이상, 타입 검증됨
sections            구간마다 timestamp + relevance_pct(0~100)
```

**타임스탬프가 있으므로 "그 영상 12분 30초에서 이렇게 말한다" 를 쓸 수 있다.**
자막 원문은 저장하지 않으므로 인용은 요약 구간을 가리킨다.

비용 통제: 30편 상한. `llm_call_logs` 에 `module='newsletter-deepread'` 로 귀속.

### S5 — 교차검증

**한 채널의 주장은 주장이고, 독립된 N채널의 주장은 사건이다.**

이번 주 실측이 이 축의 값을 보여준다:

```
딥시크 하네스   15편 · 6개 언어권 · 독립 채널 15개   → 사건
퓨리오사AI      5편 · 한국어만 · 채널 3개(경제화이팅 3편 포함)  → 사건 아님, 확인 필요
```

퓨리오사 건은 *"엔비디아를 꺾었다"*, *"1조 2천억을 거절했다"* 가 반복되는데
**교차검증이 안 된다.** 그래서 창간호가 *"이런 제목이 돈다는 것까지가 말할 수 있는 전부다"* 로 처리했다.
그 처리는 옳았고, **규칙으로 굳혀야 한다**:

> 독립 채널 3곳 미만에서만 나오는 주장은 **사실로 쓰지 않는다.** "이런 제목이 돈다"로만 쓴다.
> 외부 1차 출처(공시·보도자료·논문)가 있으면 그때 사실로 승격한다.

### S6 — 통계 (기사의 뼈대)

**떨어진 이유의 분포가 곧 기사다.** 상위 설계의 판단이고, 실측이 뒷받침한다.

읽고 싶게 만드는 것은 형용사가 아니라 **비대칭**이다. 이번 주 발견된 것들:

| 통계 | 왜 읽히나 |
|---|---|
| 딥시크 하네스 영어 11 : 한국어 4 | 영어권이 먼저 떠든다 |
| 클로드 코드 전반 한국어 50 : 영어 50 | 그런데 쓰는 이야기는 이미 반반이다 |
| 같은 스킬, 영어 20일 → 한국어 22일, 조회수 3.19배 | 시차가 숫자로 보인다 |
| 퓨리오사 한국어 5 : 영어 0 | 반대 방향도 있다 |
| 855채널 중 599개(70%)가 편당 중앙값 100회 미만 | 많이 올리는 채널일수록 안 본다 |

이 다섯 줄이 창간호의 실질이었다. **통계를 곁들이는 게 아니라 통계가 기사다.**

### S7 — 집필·검수

집필자에게 넘기는 것은 **§1 실패의 반대**여야 한다.

| 넘긴다 | 넘기지 않는다 |
|---|---|
| S3 통과분 전량 (제목·채널·조회수·길이·게시일·설명 220자) | 사람이 자른 상위 N |
| S4 요약(개체·구간·타임스탬프) | 사람이 만든 덩어리 |
| S6 통계 원표 | 사람이 쓴 해설 문장 |
| S5 교차검증 등급 | **기사의 축** |

축은 집필자가 데이터에서 스스로 찾는다. 지정하면 그 지정이 그대로 기사가 된다.

## 3. 팩트체크 — 3단 등급

발행물의 모든 주장에 등급이 붙는다. 등급 없는 문장은 발행하지 않는다.

| 등급 | 조건 | 표기 방식 |
|---|---|---|
| **확인** | v2 요약 타임스탬프 구간으로 지목 가능 | "12분 30초에서 …라고 말한다" |
| **관측** | 독립 채널 3곳 이상에서 같은 주장 | "세 채널이 같은 이야기를 한다" |
| **미확인** | 그 외 전부 | "이런 제목이 돈다" — 사실로 쓰지 않는다 |

**모든 숫자는 원장으로 되짚을 수 있어야 한다.** 조회수·편수·비율은 전부
`search_trace_candidate` / `video_pool` 행에서 나온다. 발행 후 수치 문의가 오면
그 행을 그대로 보여줄 수 있어야 한다.

---

## 4. 출처 표기

각 추천 영상에 채널명·게시일·길이·조회수(수집 시점)를 붙인다.
조회수는 변하므로 **"수집 시점" 을 명시**한다.

교차검증 등급이 "관측" 인 주장에는 근거가 된 채널 수를 적는다.

---

## 5. 채널 원장 — 주간 Top 100 (신규)

주간 발행을 지속 가능하게 만드는 실체다. 그런데 **줄 세우는 방식을 틀리면 스팸 목록이 된다.**

### 실측 — 편수 정렬은 실패한다

```
10편  편당 중앙값     4회   SVIL 시각지능 연구소
 8편  편당 중앙값     3회   Adsorp AI Hindi
 7편  편당 중앙값     4회   onepagecode   (평균 129분)
 4편  편당 중앙값     1회   Stickonomics
```

**855채널 중 599개(70%)가 편당 중앙값 100회 미만.** 많이 올리는 채널일수록 안 본다.
편수로 Top 100 을 만들면 상위가 전부 이런 채널로 찬다.

중앙값으로 줄 세우면 정상 목록이 나온다:

```
3편 중앙값 16,302회  경제화이팅
3편 중앙값  7,781회  Cloud Codes
2편 중앙값  7,600회  Jay Choi
3편 중앙값  5,036회  Tech Bridge
```

### 설계

**한 주 데이터만으로는 Top 100 이 안 된다.** 주 2편 이상 낸 채널이 **114개**뿐이다. 누적이 필요하다.

```
neighbor_score = 조회수 중앙값(최근 8주)  ×  S3 통과율  ×  발행 규칙성
                 ─────────────────────────────────────────────────
                 하한: 최근 8주 3편 이상, 편당 중앙값 100회 이상
```

- **조회수 중앙값** — 평균이 아니라 중앙값. 한 편 터진 채널과 꾸준한 채널을 구분한다.
- **S3 통과율** — 많이 올리는데 판정에서 계속 떨어지는 채널을 강등한다.
- **규칙성** — 주마다 내는지, 몰아서 내는지.
- **하한** — 70% 미시청 채널을 원천 배제.

진입·이탈은 매주 기록한다. **이탈 자체가 기사거리다** — "지난주까지 매주 내던 채널이 이번 주 멈췄다".

신규 테이블 필요: `newsletter_channels`(채널·도메인·주차별 점수·진입/이탈 이벤트).

## 6. 규모와 비용

| 항목 | 값 |
|---|---|
| 도메인 | 9개 (`tech·learning·health·business·finance·social·creative·lifestyle·mind`) |

**하루 한도 안에 9도메인이 전부 들어간다.** 요일을 나누면 여유가 더 크다.

LLM 비용은 S3·S4 에서만 발생하고 `llm_call_logs` 로 귀속된다.
**[미측정]** — S3 판정 1편당 원가, S4 심층 1편당 원가. 첫 도메인 실행 후 확정한다.

## 7. 발행물 저장 (신규)

호수·상태·정정 이력이 남아야 상용이다.

```
newsletter_issues   도메인 · 호수 · 창(from~to) · 상태(draft/review/published)
                    · 통계 스냅샷 · 발행 시각
newsletter_items    호수별 추천 영상 · 등급 · 인용 타임스탬프 · 순서
newsletter_claims   주장 · 등급 · 근거(영상 id + 타임스탬프 또는 채널 수)
```

**정정이 가능해야 한다.** 발행 후 사실 오류가 발견되면 정정 이력이 남는 구조여야 한다.

발송은 `email/broadcast` 재사용. **발송은 James 고유 권한이므로 파이프라인은 `review` 상태에서 정지한다.**
초안 작성 → 렌더 → 화면 제시 → 정지. 이것은 CLAUDE.md 하드룰이고 훅으로 강제돼 있다.

## 8. 단계별 착수 순서

각 단계가 독립적으로 되돌려져야 한다.

| # | 내용 | 되돌리는 법 | 선행 |
|---|---|---|---|
| 1 | 수확기 — 신선도 3종 + 도메인별 쿼리셋 | 코드 revert | — |
| 2 | S1·S2 게이트 + `writeSearchTrace` 배선 | 기록만 하므로 영향 0 | 1 |
| 3 | S3 판정 — `topic-judge` 재사용 + 과장 축 추가 | 플래그 off | 2 |
| 4 | S6 통계 + 집필자 패키지 산출 | 산출물만 | 3 |
| 5 | **여기서 한 호 만들어 본다** | — | 4 |
| 6 | S4 심층 + S5 교차검증 (인용 등급) | 플래그 off | 5 |
| 7 | 채널 원장 §5 | 테이블 drop | 6 |
| 8 | 발행물 저장 §7 + 발송 배선 | 테이블 drop | 7 |

**5번에서 한 번 멈춘다.** S4 심층은 가장 비싼 단계이고, 그 앞까지로 읽을 만한 호가 나오는지
먼저 확인해야 한다. 나오지 않으면 심층을 붙여도 안 나온다.

## 9. 미측정 — 확정 전 반드시 잴 것

추정치를 쓰지 않기 위해 남긴다.

| # | 잴 것 | 왜 |
|---|---|---|
| M1 | S3 판정 1편당 LLM 원가·지연 | 1,042편 판정이 감당 가능한지 |
| M2 | S4 심층 1편당 원가 | 30편 상한이 맞는지 |
| M3 | 자막 확보율 — 상위 30편 중 실제로 자막이 오는 비율 | S4 의 전제. Mac Mini SPOF, Azure 폴백 有 |
| M4 | S3 통과율 — 1,042편 중 몇 편이 살아남나 | 집필자에게 넘길 분량 |
| M5 | 9도메인 각각의 주간 수확량 | tech 외 도메인도 2,000편이 나오는지 |
| M6 | 판정 품질 — 사람이 납득하는가 | **비용보다 이게 먼저** |

M6 가 가장 중요하다. 상위 설계의 결정이 여전히 유효하다 —
**초기에는 사람이 판정하고, 그 판정을 라벨로 모아 자동화한다.**
그때 초안은 산문이 아니라 **후보 목록 + 표시·재정렬** 형태여야 한다.
산문을 고쳐 쓰면 배울 것이 남지 않는다.
