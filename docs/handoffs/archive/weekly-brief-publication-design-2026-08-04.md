# 주간 브리프 발행 — 설계

> 2026-08-04 · **설계 전용. 구현 금지 (James).**
> 이 문서의 모든 수치는 prod 실측이다. 미측정 항목은 **[미측정]** 으로 표시했고, 추정치는 쓰지 않았다.

## 0. 만들려는 것

James 예시 (문구는 예시이며 확정 카피가 아님):

> *"지난 한 주 Claude Code 에서 1,276개의 영상 중 Top 10 은 …, 핵심 내용은 1,2,3,4,5,
> 그중 중요한 내용은 무엇. 또 가장 품질이 좋은 영상은 1,2,3, 나머지 1천여 개 이상의
> 영상은 중복/과장/왜곡이 있었습니다."*

이 문장이 성립하려면 네 가지가 참이어야 한다.

| 주장 | 필요한 것 |
|---|---|
| "1,276개 중" | 실제로 그만큼 훑고, 그 수를 저장 |
| "Top 10" | **서열**이 있는 점수 (통과/탈락 아님) |
| "핵심은 1~5, 그중 중요한 것" | 여러 영상을 **가로질러** 읽은 종합 |
| "나머지는 중복/과장/왜곡" | 탈락 **사유**를 세어둠 |

## 1. 핵심 설계 판단 — 깔때기가 곧 기사다

"나머지 1,000편이 중복/과장/왜곡" 을 쓰기 위해 1,000편을 깊이 검사할 필요는 없다.
**떨어진 이유를 세면 된다.** 비싼 판정은 살아남은 소수에만 건다.

```
N편 훑음
 ├ 중복 / 시리즈 재탕     ← 기계적, 비용 0
 ├ 주제 무관             ← 적합도 게이트 (C3, 배포됨)
 ├ 쇼츠 / 낚시 제목       ← duration·blocklist, 비용 0
 ├ 얕음                  ← [설계 필요]
 └ 생존 소수 → Top N + 주간 종합   ← 여기만 비쌈
```

## 2. 이미 있는 것 — 실측

### 2-1. 탈락 사유 기록기가 **이미 존재하고 prod 에서 켜져 있다**

`search_trace` + `search_trace_candidate` (`src/modules/search-trace/index.ts`).
모듈 주석: *"every candidate video that was considered, whether each was kept or dropped (+ reason)"*.

**prod `SEARCH_TRACE_ENABLED=true` (printenv 실측).**

`series_dedup`(중복) · `shorts`/`blocklist`(낚시) · `below_relevance_min`(무관) · `off_lang`.

### 2-2. 그러나 큐레이션 경로는 trace 를 남기지 않는다

`trigger` 값이 `pool_serve` / `wizard` / `add_cards` 셋뿐이다. **큐레이션 빌드는 없다.**
그리고 최신 trace 가 **2026-07-15** — 3주 전이다.

즉 **기록기는 있고, 발행 대상 경로에 안 붙어 있다.**

### 2-3. 순위 신호는 대부분 비어 있다

23,027 후보 행 기준:

| 신호 | 채워진 행 | 비율 |
|---|---:|---:|
| `llm_pick_score` | 9,217 | 40% |
| `duration_sec` | 9,853 | 43% |
| `view_count` | 9,127 | 40% |
| `relevance_gc` | 802 | 3.5% |
| `ts_rank` | 659 | 2.9% |

모듈 주석이 이유를 적고 있다: *"cosine is absent on the whole v5 serve path"*,
*"relevance_gc is populated ONLY by async paths"*.

**Top 10 을 매길 축이 사실상 없다.**

### 2-4. 적합도는 서열용이 아님 — 실측

C3 게이트 배포 후 파이썬 편성 4편 실측:

```
#0 적합도 72 · #1 적합도 72 · #2 적합도 72 · #3 적합도 45
```

**상위 3편이 동점 72.** 통과/탈락에는 충분하나 **Top 10 서열에는 못 쓴다.**

### 2-5. 모수는 충분하다 — 실측

`파이썬`, 최근 7일, `order=date`, `regionCode=KR`:

| 검색어 | 반환 | YouTube 추정 총계 |
|---|---:|---:|
| 파이썬 | 50 (요청 상한) | **36,246** |
| 파이썬 강의 | 50 | 4,636 |
| python 강의 | 50 | 18,442 |

**"N편 중" 의 N 을 만드는 데 공급은 제약이 아니다.**

단, 같은 측정에서 상위 결과에 **영어권 채널과 쇼츠가 다수 섞였다**
(`relevanceLanguage=ko` 를 걸었음에도). 훑는 수와 쓸 수는 다르다.

### 2-6. 영상별 요약은 있고, 주간 종합은 없다

v2 rich summary = **영상 1편 단위**. 여러 영상을 가로질러 읽는 기계는 리포에 없다.

| # | 재야 할 것 | 왜 |
|---|---|---|

## 5. 설계 방향 (수치 미확정)

### 5-1. 3단계는 이미 정해진 이름 그대로다

| 단계 | 발행물 | 화면 (build 97 라이브) |
|---|---|---|
| **◎ Interest** | "지난 한 주 N편을 봤습니다" | 구독 주제 |
| **≡ Brief** | "Top 10, 핵심은 1~5" | 압축 목록 |
| **✦ Insight** | "그중 중요한 것은 X / 나머지는 …" | 한 주의 결론 |

탭 이름이 발행 구조와 같다. 이는 사후 맞춤이 아니라, 세 단계가 원래 같은 깔때기의 세 지점이기 때문이다.

### 5-2. 운영 방식 — 사람이 먼저, 자동화는 그 뒤 (James 2026-08-04)

**초기: 도메인별 초안을 만들고 James 가 전부 읽고 검토해서 내용을 채운다.
그 과정에서 쌓인 데이터로 판단 기준을 만들고, 그 다음에 자동화한다.**

이 결정이 §3 의 미해결 항목 성격을 바꾼다.

| | 이 결정 前 | 이 결정 後 |
|---|---|---|
| ② 서열 점수 | 내가 기준을 설계해야 함 | **James 의 선택이 기준** |
| ④ 과장·왜곡 판정 | LLM 이 판정할 수 있는지가 관건 | **James 의 판정이 정답 라벨** |
| M4 (판정 품질) | 사람이 납득하는지 사후 검증 | **애초에 사람이 판정** |

즉 ②④는 "설계해서 맞히는 문제" 가 아니라 **"라벨을 모으는 문제"** 가 된다.
자동화는 라벨이 충분히 쌓인 뒤의 일이고, 그때는 기준을 지어내는 대신 **관측된 결정을 재현**하면 된다.

#### 초안은 글이 아니라 서식이어야 한다 — 이 설계의 핵심 제약

James 가 산문 초안을 고쳐 쓰면 **기계가 배울 수 있는 것이 남지 않는다.** 최종 문장은
결과이지 결정이 아니다. 배울 수 있는 것은 **결정**이다:

- 후보 N개 중 **무엇을 Top 에 남겼나**
- **무엇을 뺐나**, 그리고 (가능하면) 어느 사유로
- 남긴 것들의 **순서를 어떻게 바꿨나**

따라서 초안은 **후보 목록 + 우리 잠정 순위** 형태여야 하고, James 의 작업은
**표시·재정렬** 이어야 한다. 그래야 모든 동작이 `(후보 특징 → James 판정)` 쌍으로 남는다.
산문은 그 위에 얹는다.

**이것이 지켜지지 않으면 초기 단계의 산출물은 발행물 하나뿐이고, 자동화 근거는 0으로 남는다.**

#### 보여준 것만 배운다 — 편향 주의

도메인 초안에 후보를 200편 넣으면 읽히지 않는다. 그래서 사전 필터가 필요한데,
**우리가 보여준 범위 밖은 영원히 라벨이 생기지 않는다.** 지금 순위가 잘못 떨어뜨린 영상은
James 눈에 닿지 않으므로 그 오류를 배울 수 없다.

완화 (설계 시 반영, 수치 미정 = **[미측정]**):
- 초안에 **탈락분 일부를 섞어 노출** (무작위 표본). James 가 "이건 왜 뺐지" 를 표시할 수 있어야
  현재 순위의 거짓 탈락이 라벨로 잡힌다.
- 표본 비율·개수는 James 의 검토 부담을 재본 뒤 정한다.

#### 무엇을 저장하는가

`(초안 제시 시점의 후보 특징) × (James 의 판정)` 쌍. 특징은 §2-3 의 trace 컬럼이
그대로 쓰인다 — trace 없이 초안을 만들면, James 가 판정해도 **무엇을 보고 판정했는지가
남지 않는다.** 다만 trace 는 **깔때기를 기록할 뿐 물을 채우지 않는다.** 순서는 §5-3 을 따른다.

### 5-3. 착수 순서

> **정정 (2026-08-06).** 본 문서 초판은 trace 배선을 "다른 모든 것의 선행 조건" 이라고
> 적었다. **틀렸다.** 그날 풀 유입을 재지 않고 쓴 문장이다. 실측 후 아래로 교체한다.

**0. 풀 유입 재개 — 이것이 실제 선행 조건이다.**

측정 (2026-08-06, prod):

| 항목 | 값 |
|---|---:|
| `video_pool` 총량 | 40,817 |
| **활성** | **638** (1.6%) |
| 마지막 정상 수집 | **2026-06-04** |
| 활성분 만료 — 7일 내 / 30일 내 / 그 이후 | 212 / 424 / **2** |
| 활성분 신선도 — 30일 이내 / 1년 초과 | 94 / **316** |

`batch-video-collector` 는 GitHub 쪽에서 **`disabled_manually`** 상태다. YAML 안에는 cron 두
줄(`30 7`·`30 19`)이 그대로 살아 있어 **파일만 읽으면 "하루 두 번 돈다" 로 읽힌다.**
워치독(`batch-video-collector-watchdog`)도 같이 꺼져 있어 두 달간 경보가 없었다.

끈 이유는 `trend-collector.yml` 헤더에 기록돼 있다 — *"the video collector was burning ~40k
YouTube units/day **with no consumer**"* (2026-06-06). 당시엔 맞는 판단이었고, **지금은
소비자(큐레이션)가 생겼는데 스위치만 그대로다.**

한 달 뒤 활성 풀은 2편이다. 그 상태에서는 trace 를 배선해도 **셀 것이 없다.**

1. **신선도 필터** — 수집이 `publishedAfter`·`order=date` 를 적용하지 않는다.
   2026-08-04 파일럿 121편의 `fresh30 = 0` 이 그 결과다. 유입을 재개해도 이걸 고치지 않으면
   "이번 주" 를 말하는 발행물에 쓸 수 없는 영상만 쌓인다.
2. **큐레이션 경로에 trace 배선** — 기록기·스키마·플래그는 전부 존재한다. 단
   `writeSearchTrace` 호출부는 3곳(`add-cards` · `wizard-precompute` · `pool-serve-fill`)이고
   **전부 만다라 경로**다. 큐레이션 모듈의 trace 참조는 **0건** — 붙은 적이 없다.
   초안의 후보도, 학습의 특징도 여기서 나온다.
3. **M1 측정** — 한 도메인의 주간 실 후보 수. 초안 분량과 검토 부담이 여기서 결정된다
4. **초안 서식 설계 + 1개 도메인 시범** — James 검토 부담을 실제로 재고, 표시 방식이
   기계가 읽을 수 있는 형태인지 확인
5. **라벨 축적** — 몇 주. 이 기간의 산출물은 발행물 + 라벨
6. **M6 (서열 신호 변별력) 을 라벨 위에서 측정** — 지어낸 기준이 아니라 관측된 결정과 대조
7. **자동화** — 라벨이 충분해진 뒤

**②④의 설계는 4번 이후로 미룬다.** 지금 기준을 지어내면 James 의 판정과 다를 것이고,
그때 버리게 된다.
