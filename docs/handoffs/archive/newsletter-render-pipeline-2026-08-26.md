## 1. 문제

지면을 만드는 코드가 없다는 것은 두 가지를 뜻한다.

1. 다음 호는 또 손으로 쓴다. 같은 품질이 나온다는 보장이 없다.
2. 디자인을 고치려면 본문 390행을 다시 건드린다. 지난 호는 영원히 옛 디자인으로 남는다.

**조악한 디자인보다 이쪽이 먼저다.** 구조를 안 가르면 디자인 개선 자체가 매번 수작업이 된다.

## 2. 구조 — 문서 하나, 렌더 셋

```
IssueDocument (JSON)
      |
      +-- renderMail()  -> 발송 메일      [존재: buildBriefEmail]
      +-- renderWeb()   -> 공개 지면      [신규 · 디자인 수신 대기]
      +-- renderNote()  -> book_json 절   [신규 · 노트 누적]
```

마스터 명세 §14 의 배포 3면(Web Report / YouTube / App Note)과 같은 구조다.
콘텐츠는 한 번만 쓰고, 표현은 면마다 다르다.

### 2-1. IssueDocument

발행 단위의 SSOT. `newsletter_issues.content_json` 에 저장한다.

```
issue      : 카테고리 · 호수 · 발행일 · 헤드라인 · 리드
stages[]   : 대단원 (제목 · 부제 · 본문 블록)
claims[]   : 주장 + 등급(확인/관측/미확인) + 출처 ref
refs[]     : 출처 목록
terms[]    : 용어 + 왜 중요한가 + 실무 문장
stats[]    : 수치 (수집 편수 · 교차확인 편수 · 등급 단계)
videos[]   : 추천 영상 (노트 누적 대상)
```

이번 호 실측 규모: 스테이지 6 · 클레임 132(교차 17 / 단일 31 / 형식 84) · 등급배지 23 · 출처 27 · 용어 5 · 데이터 7행.
**개수는 매주 다르다. 개수에 의존하는 레이아웃은 금지.**

### 2-2. 디자인 개선을 어떻게 적용하는가 — 이 설계의 핵심

버전을 둘로 나눈다.

| 버전 | 무엇이 바뀔 때 | 빈도 |
|---|---|---|
| `schema_version` | 실리는 **내용의 종류**가 바뀔 때 (새 블록 추가 등) | 드묾 |
| `template_version` | **생김새**가 바뀔 때 | 개선할 때마다 |

**발행 시점에 HTML 을 굽지 않는다. 읽을 때 렌더한다.**

구워 두면 디자인 개선이 앞으로 낼 호에만 닿고 지난 호는 옛 모습으로 남는다.
읽을 때 렌더하면 `template_version` 하나를 올리는 것으로 **과거 전 호가 한 번에 새 디자인이 된다.**
비용은 요청당 렌더인데, `(issue_id, template_version)` 키 캐시로 흡수한다.
키가 버전을 포함하므로 템플릿을 올리면 캐시가 자동으로 갈린다. 별도 무효화 절차가 필요 없다.

**롤백**: 새 템플릿이 특정 호에서 깨지면 그 호만 `template_version` 을 고정한다. 전체를 되돌릴 필요가 없다.

### 2-3. 템플릿이 사는 곳

```
src/modules/newsletter/
  issue-schema.ts        zod. IssueDocument 계약
  render-web.ts          템플릿 선택 + 슬롯 주입
  render-note.ts         book_json 절 생성
  templates/
    web-v1/              Claude Design 산출물 (수신 대기)
    web-v2/              다음 개선분. v1 은 남긴다
```

디자인 개선 = `templates/web-v2/` 추가 + 기본값 변경. **기존 파일을 고치지 않는다.**
CC 는 슬롯을 채우기만 하고 시각 설계는 하지 않는다(James 지시).

## 3. 지면을 무엇이 서빙하는가

현재 `insighta.one/brief/*.html` 은 nginx 정적 서빙이라 SPA 폴백이 걸린다.
**없는 경로도 200 을 돌려준다** — 창간호 배포 때 실제로 이 거짓 200 에 한 번 물렸다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A (권장)** | API 가 `GET /brief/:slug` 로 HTML 서버 렌더 | 공유 미리보기·검색 노출·JS 없이 열림. 장문 문서에 맞음 | ingress 경로 1줄 추가 |
| B | FE 라우트가 API 에서 받아 주입 | 인프라 무변경 | 공유 카드·검색 노출 없음. 브리프는 공유가 목적이라 치명적 |

**A 를 권한다.** 브리프는 공유되라고 만드는 물건이고, 미리보기 없는 링크는 공유되지 않는다.

## 4. 콘텐츠는 누가 넣는가

admin 등록. James 확정 사항 — *"제품 내에서 만들어져야 한다."*
admin 이 IssueDocument 를 등록하면 제품이 세 면을 찍는다. CC 가 손으로 HTML 을 쓰는 경로는 폐기한다.
