# 주제 풀 파이프라인 — 설계

> 2026-08-04 · 큐레이션 서빙 품질 트랙
> 이 문서는 하루치 진단의 종착점이다. 진단이 세 번 자리를 옮겼고(적합도 게이트 → 쿼리 생성 → 수집 파이프라인 정지), 그 이동 자체가 설계 근거라 §1 에 남긴다.

## 0. 결정 (James, 2026-08-04)

**쓰레기 유입 불가.** 좋은 영상을 잃더라도 무관한 영상이 편성에 들어오는 것보다 낫다.

이 결정은 코드에 박혀 있던 반대 원칙을 폐기한다:

> `src/modules/curation/config.ts:72` — *"NO rung combination may end at an empty week (덜 정렬된 카드 > 카드 0장, the converged serving principle)"*

그 원칙이 사다리를 코사인 0.5 → 0.35 로 내리게 했고, 4주 전 서빙분을 재유입시켰고, 파이썬 편성에 스페인어 회화를 앉혔다. 원칙이 잘못 읽힌 게 아니라 **원칙이 그 결과를 만들었다.**

**목표 (James):** 핵심 주제 10개 · 주제당 매일 200~300편 수집 → 일 2,000~3,000편 → 필터 → 고품질 1,000편 가까이 축적. 니치 도메인은 당장 대응이 어려우므로 점진 확대.

## 1. 왜 라이브 검색으로는 안 되는가 (측정)

빌드 시점에 검색해서 그 주 편성을 만드는 구조는 **엄격한 게이트와 양립할 수 없다.** 통과율을 올리면 쓰레기가 들어오고, 통과율을 지키면 양이 안 나온다.

2026-08-03 04:03, 활성 파이썬 구독 실측:

```
curation fresh leg  topic=파이썬  windowDays=30  searched=4  fitDropped=3  picks=1
```

30일치 검색에서 후보 4편. 채널은 라이프해커·자청 / 유튜브신쌤 / 지투지 — 자기계발 채널이다. 나머지 16칸은 풀 사다리가 코사인 0.35 로 채웠고, 그 결과가 스페인어 3편·메이크업·기타 연주·lofi·다른그림찾기다.

쿼리 생성을 고친 뒤(#1459, 2026-08-04 04:41) 재빌드:

```
curation topic shaping  degraded=false  queryCount=8  latencyMs=5414
  subGoals: [파이썬 기초 문법과 데이터 타입 학습 / 함수와 모듈을 활용한 코드 구조화 /
             파이썬으로 웹 크롤링 및 자동화 구현 / 판다스와 넘파이를 이용한 데이터 분석 /
             장고 또는 플라스크로 웹 애플리케이션 개발 / 머신러닝과 사이킷런 기초 이해 /
             파이썬 디버깅과 예외 처리 능력 / 실무 프로젝트로 파이썬 포트폴리오 구축]
fresh: { picks: 0, fitDropped: 1, windowDays: 7 }
picked: 16   ← 전부 풀 사다리
```

**쿼리는 고쳐졌는데 편성은 그대로다.** 하위주제 8개 전부 진짜 파이썬이고 커버리지도 8/8인데, 신선 픽은 1 → 0으로 오히려 줄었다.

이유는 저수지가 말라 있어서다:

| video_pool source | 총량 | 최근 30일 |
|---|---:|---:|
| batch_trend | 29,397 | **0** |
| yt_promoted | 7,138 | **0** |
| v2_promoted | 3,566 | 47 |
| user_playlist | 386 | 0 |
| curation_weekly | 2 | 2 |

**4만 편 중 최근 30일이 106편.** 사다리가 2019~2020년 영상을 고른 게 아니라, 고를 수 있는 게 그것뿐이었다.

수집은 2026-06-04 에 멈췄다:

```
2026-06-04 21:10  daily_trend  success  found 5649  new 708  quota 20113
2026-06-04 10:48  daily_trend  success  found 5661  new 635  quota 20114
(이후 없음)
```

정지 사유 유력 후보 = CP496 의 의도적 cron off(2026-06-06, *"소비자 0 확정"*). 날짜가 맞는다. **당시 판단은 옳았고 전제가 바뀌었다** — 그땐 풀 소비자가 없었고 지금은 큐레이션이 소비자다. 확정에는 Mac Mini crontab 확인이 필요한데 현재 다운(2026-08-03 실측).

## 2. 이미 존재하는 것

새로 만들 게 거의 없다. **기계는 있고, 두 달 전에 멈췄고, 가운데 한 단계가 비어 있다.**

| 부품 | 상태 |
|---|---|
| `video_pool` | 40k행. 살아 있음, 신규 유입만 정지 |
| `video_pool_domain_tags` | 29,942행 / 7 도메인. 인덱스 `(domain, relevance_score DESC)` |
| `video_pool_collection_runs` | 실행 원장 (`quota_used` 포함). 마지막 06-04 |
| `batch-video-collector` | 플러그인 존재 (`executor.ts`, `manifest.ts`) |
| `generateMandalaWithQueries` | 주제 → 하위주제 8 + 셀 쿼리 8. #1459 로 큐레이션에 배선됨 |
| `computeCardRelevance` | LLM 적합도 판정 |
| `curationPoolAdmission` | duration + blocklist |
| `embedBatch` / 코사인 | 임베딩 유사도 |

**API 검색 키 8개 = 일 80,000 유닛** (prod printenv 실측). 메모리의 "8→1 키" 기록은 stale.

## 3. 비어 있는 세 칸

### ① 필터가 존재한 적이 없다 — 가장 큰 결함

`video_pool_domain_tags.relevance_score` 가 **29,942행 7도메인 전부 `0.50`**, 기본값 그대로다. 테이블의 존재 이유인 `(domain, relevance_score DESC)` 인덱스가 **정렬 키가 상수라 무의미**하다.

James 표현의 `수집 > 필터거쳐서 > 좋은품질 확보` 에서 **가운데가 통째로 빈다.** 지금 더 모으면 더 큰 무정렬 더미가 될 뿐이다.

### ② 태그 키가 너무 굵다

도메인이 `기술/개발`·`학습/교육` 같은 7개 버킷인데 구독은 `파이썬`이다. `기술/개발`을 파이썬 구독자에게 주는 것이 **오늘 관측한 실패 그 자체**다.

`domain VarChar(50)` + 유니크 `(video_id, domain)` 이므로 **주제 문자열을 그대로 키로 쓸 수 있다.** 한 영상이 여러 주제 태그를 갖는 것도 그대로 된다. **스키마 변경 불요.**

### ③ 모아둔 것이 30일 뒤 사라진다

`video_pool.expires_at` 기본 `now() + 30 days`. 큐레이션 행만 1년 예외(유령 카드 사고 대응). 표적 수집분에 TTL 정책이 없으면 **서빙 전에 만료돼 쿼타를 버린다.**

## 4. 파이프라인

```
주제 (핵심 10)
  └─ 하위주제 8 + 쿼리 8          generateMandalaWithQueries, 주제당 1회 생성 후 재사용
       └─ 수집  8 × search.list   → 후보 ~240/주제/일
            └─ 필터 (아래 캐스케이드)
                 └─ video_pool + domain_tags(domain=주제, relevance_score=판정값)
                      └─ 서빙: (domain, relevance_score DESC) - 사용자별 이력 제외
```

### 필터 캐스케이드 — 순서가 비용을 결정한다

비싼 판정이 작은 집합만 보도록 **싼 것부터** 건다.

| 단계 | 수단 | 비용 | 떨구는 것 |
|---|---|---|---|
| 1 | 이미 풀에 있는 video_id | 0 | 중복 |
| 2 | `curationPoolAdmission` (duration 60~3600, blocklist) | 0 | 쇼츠·초장편·스캠 |
| 3 | 언어 / 채널 다양성 | 0 | 오프language·채널 과점 |
| 4 | 임베딩 코사인 vs 주제 | 낮음 (배치) | 명백한 무관 |
| 5 | `computeCardRelevance` LLM 판정 | **높음** | 미묘한 무관 |

**5단계는 fail-closed.** 판정에 실패한 영상은 좋은지 나쁜지 *모르는* 영상이고, §0 기준에서 모르는 것은 못 들여보낸다. 현재 신선 레그 코드는 반대로 되어 있다:

```js
} else {
  scored.push({ card, relevancePct: CURATION_RELEVANCE_FLOOR });  // 판정 실패 = 통과
}
```

주석에 *"an LLM outage must not empty the week"* 라고 적혀 있는데, **그것이 §0 에서 폐기된 원칙이다.**

`relevance_score` 에는 5단계 결과를 쓴다. 그래야 `(domain, relevance_score DESC)` 가 처음으로 의미를 갖는다.

## 5. 쿼타 검산 (측정값 기반)

- `search.list` = 100 유닛/콜, `BATCH_COLLECTOR_SEARCH_MAX_RESULTS = 30`
- 주제당 1회 = 8 쿼리 × 100 = **800 유닛**, 후보 8 × 30 = **240편** (James 의 "200~300" 과 일치)
- 10 주제 × 1회/일 = **8,000 유닛/일**
- `videos.list` 메타 = 1 유닛/50건 → 2,400편 = 48 유닛 (무시 가능)

**일 8,048 / 80,000 = 10%.** 위저드·add-cards·큐레이션 빌드가 쓰고도 남는다.

옛 브로드 스윕과 비교하면 표적 수집이 압도적으로 싸다:

| | 유닛/회 | 신규 영상 | 유닛/신규 1편 |
|---|---:|---:|---:|
| 옛 daily_trend | 20,113 | 300~700 | **~30** |
| 표적 수집 (10주제) | 8,000 | ~2,400 후보 | **~3** |

**쿼타는 병목이 아니다.** 병목은 §3-① 이다.

### 실제 비용은 5단계 LLM

일 2,400 후보가 전부 5단계까지 가면 비싸다. 1~4 단계가 대부분을 떨궈야 하고, **1~4 통과율과 5단계 통과율을 실측한 뒤에** 상한을 정한다. 첫 배포는 **1개 주제 · 수집만 · 5단계 이전까지** 로 측정 후 확장.

## 6. 착수 순서

§0 기준이 순서를 정한다 — **자르는 것이 먼저, 채우는 것이 다음.**

1. **적합도 게이트를 단일 길목으로 + fail-closed.** 어느 레그로 들어왔든 판정을 지난다. 지금 16/16 이 판정 0회로 들어온다. 레그마다 복제하면 다음 레그에서 또 빠진다 (같은 계열 3회 재발 기록).
2. **사다리는 recall 만 넓힌다.** 기간·제외 범위는 넓히되 **문턱은 고정.**
3. **짧은 주·빈 주 합법화** + 스냅샷 보존. `config.ts:72` 주석 폐기.
4. **넓히기 조건 수리.** 현재 `if (!v5.cards.length)` — *검색 결과가 0일 때만* 넓힌다. 쿼리를 고치자 7일 창에 쓰레기 1편이 잡혔고 **그 1편 때문에 30일 확대가 봉쇄됐다**(2026-08-04 실측). `picks < 목표` 로 바꾼다.
5. **표적 수집 1주제 파일럿** — 수집 + 1~4단계 필터, 통과율 실측.
6. 실측 기반으로 5단계 상한 설계 → 10주제 확대.

1+4 는 한 PR 로 묶는다. 따로 가면 그 사이 편성이 비어 보인다.
